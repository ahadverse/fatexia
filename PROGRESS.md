### Messaging (rebuilt 2026-07-26)

The first cut worked for the happy path but got read state wrong. `readAt` records that the **recipient** read a message, and which party that is depends on the message's direction — the network's inbox is `INBOUND`, the affiliate's is `OUTBOUND`. That was implicit, and four things followed from it:

1. **The affiliate could never mark anything read.** There was no affiliate-side read route at all, so the `unreadMessages` tile on their dashboard counted `OUTBOUND && readAt IS NULL` and could only ever go up. Permanently stuck.
2. **`PATCH /messages/:id/read` had no direction check.** Keyed only on a message id, it had no way to know whose inbox the caller meant — an admin calling it on an `OUTBOUND` message silently cleared the *affiliate's* unread state.
3. **The admin thread list was assembled from one page of raw messages** (`pageSize: 200`, grouped in JS). Past 200 messages network-wide, whole conversations silently disappeared from the sidebar — and 200 was already the schema's maximum page size.
4. **Opening a thread fired one HTTP request per unread message.**

Fixed by making the two inboxes explicit rather than incidental:

- Read state is now marked **per conversation, per side**: `PATCH /messages/threads/:affiliateId/read` (network) and `PATCH /messages/mine/read` (affiliate). Each names its own direction, so one side's acknowledgement structurally cannot touch the other's. Both are a single bulk `UPDATE` guarded by `readAt IS NULL`, which also makes them idempotent — re-opening a thread never rewrites existing timestamps.
- `PATCH /messages/:id/read` was **removed**, not guarded. Neither UI marks individual messages (you read a conversation), and deleting the unsafe shape is better than defending it.
- New `GET /messages/threads` aggregates conversations **in SQL** (`COUNT(*) FILTER` for unread, `DISTINCT ON` for the newest message per thread), so the list is complete at any message volume and paginates over *conversations*. Preview text is truncated server-side rather than shipping whole 5,000-character bodies to render one line.
- New `GET /messages/threads/:affiliateId` and `GET /messages/mine` return a whole conversation, oldest first.
- New `GET /messages/mine/unread-count` for the affiliate badge.
- Both UIs mark read as an effect of the conversation loading, so it also fires for the thread auto-selected on first render — not just on an explicit click.
- [x] Verified with `node scripts/dev/verify-messaging.js`, which drives a real exchange between the seeded admin and affiliate and asserts all 15 conditions: each side's unread rises only on messages it received, each side's acknowledgement clears only its own count, re-acknowledging marks 0 further rows, the grouped thread list agrees with the counts, and the retired per-message route now 404s.

## Tracker

Runs as a second entrypoint (`src/tracking.ts`, `npm run dev:tracking` / port 4001) in the same `backend/` package — not a separate project, matching PLAN-tracker.md's "same language, separate process" design. Reads offers directly from the shared Postgres DB.

- [x] `/click?offerId=&affiliateId=&sub1=&sub2=&sub3=` — resolves the offer (single indexed PK read), runs the fraud checks that are currently active, generates the click_id, fire-and-forget logs the click, 302-redirects to `destinationUrl` with `{click_id}` substituted (or to a neutral fallback if scored BLOCKED). The `sub1/2/3` pass-through parameters and the referer were added 2026-07-25 and are stored on the click row (length-capped, since they are affiliate-controlled free text on a public endpoint) — this is what the Sub-ID report reads, and keeping them on the click rather than only the conversion means the report can show click volume per sub-id, not just converted traffic.
- [x] `clicks` table/module in the Backend (entity + migration) — offerId/affiliateId indexed, ip, UA-parsed device/os/browser, countryCode, asn, isDatacenter, isProxyOrVpn (nullable), riskScore, qualityStatus (GOOD/SUSPECT/BLOCKED/UNSCORED)
- [x] `geo-source` module — MaxMind GeoLite2 City+ASN lookup, degrades gracefully (returns unknown, logs a warning, doesn't crash) when the `.mmdb` files aren't present
